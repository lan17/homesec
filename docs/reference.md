# HomeSec public behavior reference

The maintained [OpenSpec capability specifications](../openspec/specs/) describe HomeSec's public behavior. Use them for requirements, lifecycle transitions, failure outcomes, and compatibility. Use the generated API contract for declared request/response models, the [error-envelope contract](../openspec/specs/integration-contracts/spec.md#requirement-canonical-api-exception-responses) for custom errors and known schema gaps, and the existing guides for deployment procedures.

The initial baseline describes the implementation reviewed on **2026-10-10**. It covers the major public surfaces and critical scenarios, rather than every setting, device, timing edge case, or failure combination. Existing tests were inspected as evidence; local baseline validation did not execute application tests or physical-device checks. Structural and documentation validation do not certify runtime conformance.

## How to read the baseline

The [shared API preconditions](../openspec/specs/integration-contracts/spec.md#shared-api-preconditions) define admission gates and authentication alternatives. Endpoint-specific responses do not override earlier authentication, mode, availability, or parsing failures. [Scenario evidence](behavior-evidence.md) distinguishes retained source review, isolated helper/excerpt checks, repository-boundary tests, and physical QA. A requirement-level test link or green CI is not proof of every scenario.

| Observation | What it establishes | What it does not establish |
| --- | --- | --- |
| Returned stage result | That invocation produced a handled result | Preservation in a later whole-state database snapshot |
| Persisted snapshot or lifecycle event | That stored observation, when readable | Complete event history, independent identity after ID reuse, or atomic coordination with files |
| Final local dump or successful upload | Artifact publication or that storage operation's result | A later backup record still being `success`, or all housekeeping completing |
| Accepted HTTP operation | Admission or scheduled work specified by the response | Completed runtime activation, playable media, or successful notification delivery |
| Detector's empty class list | No accepted detections were returned | Positive-frame or complete decoding, or safety of destructive cleanup |

## Time origins

Local-folder clip start/end values are estimates from file mtime and a fixed 10-second duration; FTP uses mtime and its `default_duration_s`. Both use naive process-local datetimes, not verified camera capture times. Event queries and clip-creation statistics use the Postgres record's database creation time, which ID reuse preserves. Lifecycle event timestamps are generated separately, and notification `ts` is a naive process-local time generated when the pipeline builds the alert. These times are not interchangeable. See the [local source](../src/homesec/sources/local_folder.py), [FTP source](../src/homesec/sources/ftp.py), [repository](../src/homesec/repository/clip_repository.py), [Postgres store](../src/homesec/state/postgres.py), and [pipeline](../src/homesec/pipeline/core.py).

## Known limitations and evidence limits

The following observations bound the baseline. They identify current defects, documentation disagreements, pending features, or incomplete verification; they do not establish promises to preserve those behaviors. Corrective behavior changes require their own reviewed spec changes. The capability headings below are durable links from the maintained specs.

### Setup configuration

- **Validation-only setup is not full apply validation.** The [finalizer](../src/homesec/services/setup.py) assembles core models and checks camera presence and the required DSN environment value before its validation-only return. It does not validate that candidate through the full backend/plugin/reference path used by [configuration replacement](../src/homesec/config/manager.py). A request with `validate_only: true` and camera backend `unknown_source` can therefore report success with no errors even though apply rejects that backend before saving. An actual-service characterization used a fake application and temporary config path; it did not start a runtime or contact a database. Validation-only success is not proof that the configuration is applicable; a committed mounted-route regression test remains follow-up work.

- **Patches, removal, and disabling have distinct validation semantics.** The [configuration manager](../src/homesec/config/manager.py) recursively merges existing-object/patch-object pairs, removes visited keys supplied as `null`, and replaces lists/scalars. An empty object does not clear existing object keys; a top-level null source patch means no patch. Subsequent defaults and validation determine effective values. Camera removal does not cascade default-policy override removal and can fail whole-config reference validation. [Configuration validation](../src/homesec/config/validation.py) still checks disabled sources/notifiers and analyzer settings in `never` mode; only alert-policy plugin validation has the stated enabled guard. These checks do not imply construction or provider calls.
- **Setup success means the selected probe passed.** The [setup service](../src/homesec/services/setup.py) aggregates individual preflight checks and dispatches registered backend probes or category-specific fallbacks. Generic plugin ping is not necessarily an upload/inference/delivery test. Probe success is neither an end-to-end processing result nor guaranteed future connectivity.

- **Redaction is field-name and userinfo based, not general secret removal.** The [shared redaction helper](../src/homesec/api/redaction.py) masks strings using case-insensitive sensitive-key substrings (`password`, `secret`, `token`, `api_key`, `credential`, `dsn`, `private_key`, `connection_string`, `passphrase`, and `bearer`), with an `_env` suffix exception for environment references. For other URL-named string fields, it removes username/password userinfo but preserves the path, query, and fragment. For example, `rtsp_url` containing `rtsp://user:password@camera/live?token=example-secret` becomes `rtsp://***redacted***@camera/live?token=example-secret`; without userinfo, a URL such as `rtsp://camera/live?password=example-secret` is unchanged. The helper does not broadly mask non-string values or unrecognized field names. Do not treat returned configuration as safe to share without inspecting it. API-boundary characterization coverage remains pending; broader secret removal requires a separate fix.
- **Case-only backend changes can discard omitted settings.** The [configuration manager](../src/homesec/config/manager.py) compares the raw patch backend to the saved normalized identifier before [model normalization](../src/homesec/models/config.py). Patching a saved `local_folder` camera with `source_backend: LOCAL_FOLDER` and only `poll_interval: 2` takes the backend-switch path: an omitted custom `watch_dir` is lost and can default to `recordings`. For preservation, omit the backend or send the exact saved normalized identifier. A discarded required field can instead make validation fail; the invalid configuration is then not saved. This is a current defect, not intended case-sensitive backend identity; focused persisted-patch coverage remains pending.

- **Saved and active configuration can differ after failure.** Setup persists configuration before activation. Runtime rollback preserves the prior runtime, but does not establish rollback of the saved file. Camera create, update, and delete also save before their optional reload request: a busy or failed reload can return an error after a successful save. Retrying that camera creation then conflicts with the name already saved. Focused persisted-mutation/create-retry coverage was not identified; the existing route tests establish error responses. See the [setup service](../src/homesec/services/setup.py), [camera routes](../src/homesec/api/routes/cameras.py), and [runtime manager tests](../tests/homesec/test_runtime_manager.py).
- **First-run setup and camera editing are the supported editing surfaces.** Setup finalization is bootstrap-only. The settings page links several settings to setup, but this does not provide a general configuration editor or a general configuration PATCH endpoint. A broader editor remains a separate feature.

### Capture recording

- **FTP rejection does not guarantee file removal.** [FTP handlers](../src/homesec/sources/ftp.py) attempt configured deletion of disallowed or incomplete uploads, log unlink failures, and can leave those files present without handing them off. Filename/mtime eligibility also does not establish decodable media; see [empty detection](#analysis-alerts).

- **Clip IDs are global within a state store, and collisions are not rejected at ingestion.** The [local-folder source](../src/homesec/sources/local_folder.py) and [FTP source](../src/homesec/sources/ftp.py) use filename stems. Thus two cameras ingesting `20261011_120000.mp4` produce the same ID despite different directories or camera-grouped storage destinations. [Initialization](../src/homesec/repository/clip_repository.py) writes fresh initial state, and the [Postgres store](../src/homesec/state/postgres.py) keys records only by `clip_id` and replaces their JSON state on conflict while preserving the original database `created_at`. Successful re-ingestion can replace the prior camera/path/results or a deletion mark, and lifecycle events share that same identity. Local repeat suppression is not a global uniqueness check; FTP has no completed-upload ID suppression. Selected notifications reuse that ID as `dedupe_key`, so recipients cannot assume it distinguishes independent clips. Independent clips need distinct IDs across cameras and prior records; HomeSec does not enforce that precondition. Cross-camera collision and repeated-FTP-after-deletion checks remain pending. This is not an intentional overwrite or replay contract.

- **Finite RTSP retry exhaustion stops that camera's monitoring.** The camera source worker ends while the runtime process remains available. Later camera availability does not resume monitoring until runtime reload or process restart creates another source worker. `max_attempts=0` retries indefinitely. The [RTSP source](../src/homesec/sources/rtsp/core.py) supports this consequence; a focused end-to-end exhaustion/recovery test was not identified.
- **Repeat suppression is not durable processing replay.** The local-folder source accepts an ID before callback completion, and the source boundary contains callback failures. It does not guarantee retry of failed processing or exactly-once delivery. Manifest-based restart suppression is source-supported without a focused restart test identified. The `*.mp4` glob follows platform case rules; uppercase `.MP4` is excluded where matching is case-sensitive, unlike FTP's case-insensitive extension allowlist. Focused uppercase local-ingestion coverage was not identified. See the [local-folder source](../src/homesec/sources/local_folder.py).
- **Publication conditions do not prove universal media integrity.** Native finalization and legacy recording use different checks; a nonempty file alone does not prove playable media. The baseline does not promise universal codec/hardware compatibility or gapless rotation. Failed native recordings can leave excluded `.partial` files; this does not mean every finalization failure produces a scanned MP4. See the [shared-media guide](shared-rust-media.md).
- **The README startup flag example has a compatibility limit.** `stream.ffmpeg_flags` is ignored by current startup preflight while automatic negotiation is enabled. Do not use that example as a guarantee of current startup control.

### Storage retention

- **Destination preparation is outside upload retry containment.** The [path builder](../src/homesec/storage_paths.py) sanitizes segments, then normalizes the path. Camera `.` can lose its segment; camera `..` can raise before an upload attempt. The [upload stage](../src/homesec/pipeline/core.py) calls this builder before its retry/error handler. An escaping preparation exception can abort the later pipeline upload join instead of becoming noncritical `UploadError`. Isolated path/stage checks do not establish the full orchestration path; that consequence is source-derived.
- **Retention eligibility is a selection-time snapshot.** The [pruner](../src/homesec/retention/pruner.py) captures pathname/state/size before deletion, then unlinks without current-state or file-identity revalidation. A same-path replacement can be deleted using the original measured size for accounting. Unlink failures can exhaust candidates while leaving usage over the cap. Retention does not call backend deletion or mutate workflow state, but a stored URI aliasing the selected physical file is not an independently protected copy. The pathname replacement was characterized in isolation, not with a live FTP/Postgres race.
- **Cleanup recheck configuration is YOLO-shaped, not generic plugin support.** The [cleanup builder](../src/homesec/maintenance/cleanup_clips.py) accepts `YoloFilterConfig` or a dictionary valid as one, uses `yolo11x.pt` by default for recheck, and retains the configured backend identifier. Other model shapes can fail before candidate processing. Normal pipeline extension support does not establish cleanup compatibility.
- **Applied cleanup can delete footage that yielded zero decoded frames.** Cleanup branches on the returned empty class list, not positive `sampled_frames` or complete decoding. A returned zero-frame result can reach local/stored deletion in applied mode; default dry run preserves originals and workflow state. A raised detector exception instead takes the analysis-error path. Do not interpret an empty result as proof the footage was inspected. The decoder cases were isolated checks; the destructive cross-capability consequence was source-traced, not an end-to-end deletion test. See the [detector](../src/homesec/plugins/filters/yolo.py) and [cleanup](../src/homesec/maintenance/cleanup_clips.py).

- **Deletion is not terminal under concurrent writes or ID reuse.** The [API](../src/homesec/api/routes/clips.py) marks a clip deleted before requesting storage deletion and does not roll that mark back on storage failure. However, a [processing-stage snapshot](../src/homesec/repository/clip_repository.py) read before the mark can later overwrite it through a whole-state [Postgres upsert](../src/homesec/state/postgres.py), even with all writes successful. Transition checks apply to the loaded snapshot, not a database-level compare-and-swap. Re-ingesting the same ID can also replace a deleted record with fresh initial state. Default lists can then expose the identity again; this does not restore removed media, and continuing processing can still attempt its upload or notification. API deletion does not cancel in-flight clip work. Cleanup's recorded outcomes are also subject to competing snapshot writes. These source-derived interleavings are not yet established by focused concurrent-database tests; see the [processing consistency limits](#analysis-alerts).

- **API deletion can leave a separate original recording.** The route marks the clip `DELETED` and deletes its stored object, without separately unlinking the original recording. While the recorded status remains `DELETED`, that original is ineligible for retention, which requires `DONE`, and maintenance cleanup excludes deleted rows. Competing writes or ID reuse can change that status as described in this section. If the stored object and original share a physical file, storage deletion can already remove it. A separate original can otherwise remain indefinitely and contribute to measured usage. All-copies deletion semantics and deletion recovery remain unresolved; no focused deletion/retention interaction test was identified. See the [clip routes](../src/homesec/api/routes/clips.py) and [retention pruner](../src/homesec/retention/pruner.py).
- **Successful upload alone does not make every local file reclaimable.** Exhausted filter failure attempts to record `ERROR` and exits without marking processing complete, even if upload succeeded. For a non-deleted clip, successful persistence without a competing snapshot write leaves `ERROR`; an older upload snapshot can overwrite that status. Concurrent writes can also lose a successful upload's recorded URI, so successful upload alone is not proof of retention eligibility. Discovered MP4s without readable state are also ineligible. No automatic whole-clip processing replay or reclamation path was found for files while they remain ineligible; recovery or manual intervention can be necessary. Do not assume every orphan directory is discovered. See the [pipeline](../src/homesec/pipeline/core.py).
- **Retention is not a hard total-disk bound.** Pruning is triggered using eligible uploaded/completed bytes, while reported usage measures discovered local bytes. Protected files can leave usage above the configured limit even after pruning. The baseline preserves selection-time eligibility and oldest-first deletion attempts when pruning occurs, without adopting the disputed trigger as an intended universal budget policy.
- **Local storage performs syntax checks, not symlink confinement.** Destinations are validated and constructed relative to the configured root, but existing symlinks can be followed during copy. See the [local storage backend](../src/homesec/plugins/storage/local.py).
- **Cleanup media deletion and workflow persistence are not atomic.** Repository writes are best-effort, so media deletion can succeed while state/event persistence fails. Default dry-run preservation is source-supported, but a focused test proving preservation of original media and workflow state/events was not identified. See the [cleanup implementation](../src/homesec/maintenance/cleanup_clips.py).
- **Deletion can report not-found after a lookup failure.** The shared lookup limitation is described under [events playback](#events-playback); HTTP 404 alone does not prove that the clip never existed.

### Analysis alerts

- **Empty or partial detection is not complete media inspection.** The [YOLO worker](../src/homesec/plugins/filters/yolo.py) returns an ordinary result if the reported frame count is zero or a read returns failure. Zero-frame cases can return empty classes, zero confidence, and `sampled_frames: 0`; later read failure returns accumulated results without an incomplete-decoding flag. Isolated fake-decoder checks establish these worker branches, not real-decoder quality. The [cleanup consequence](#storage-retention) is separate from a raised detector exception.
- **Retry budgets do not bound elapsed time or all preparation failures.** The shared [stage runner](../src/homesec/pipeline/core.py) bounds attempts/backoff without a generic deadline around `await op()`. A hung operation can remain pending, and notifier fan-out can wait for one entry after others settle. Upload destination preparation is outside the handled retry boundary; its exception can abort the later join before alert evaluation/completion. Backend timeouts and shutdown behavior remain separate.
- **Structured analysis is schema-validated, not verified against footage.** The [analysis models](../src/homesec/models/vlm.py) use string timestamps and do not validate frame-count agreement, nonnegative frame counts, or entity chronology against sampled images. The [analyzer](../src/homesec/plugins/analyzers/openai.py) validates structure; accepting that structure does not certify visual or temporal truth.

- **Successful concurrent writes can still lose metadata or status.** Upload and filtering run concurrently in the [pipeline](../src/homesec/pipeline/core.py). The [repository](../src/homesec/repository/clip_repository.py) independently reads, changes, and saves each stage's snapshot; the [Postgres upsert](../src/homesec/state/postgres.py) replaces the whole JSON document. If upload and filtering read the same earlier state, a later filter write can erase the upload URI, or a later upload write can erase filter results. An older snapshot can likewise overwrite a filter-error or deletion status without any database exception. Collecting the eventual upload outcome returns in-memory metadata to the pipeline; it does not repair the persisted snapshot. Event queries, playback, and retention use whatever state survives, not necessarily all successful stage outcomes. The [shared-object state fake](../tests/homesec/mocks/state_store.py) returns the same mutable objects and can conceal this production snapshot distinction. The interleavings are source-derived; deterministic barrier-controlled tests using independent serialized snapshots remain pending. Best-effort persistence is not a concurrency-safety guarantee.

- **Detector setting names do not fully explain their current semantics.** YOLO `sample_fps` is a frame-index stride; `min_hits` counts distinct classes for early exit rather than suppressing below-threshold results. Its supported target mapping is narrower than some README examples. The baseline describes supported results and acceptance checks, without deciding revised settings or expanding detector promises. Existing detector tests exercise boundaries rather than real-model accuracy. See the [YOLO implementation](../src/homesec/plugins/filters/yolo.py).
- **An absent analysis can produce a misleading reason.** The default alert policy uses `filter_detected_trigger_vlm_failed` when motion notification is disabled, analysis is absent, and a trigger is detected, including intentional `never` mode. Enabled motion notification takes precedence with `notify_on_motion=true`. `never` skips analysis; it does not itself disable notification. The reason is not proof of a provider failure. See the [default policy](../src/homesec/plugins/alert_policies/default.py).
- **Some critical boundaries remain source-supported.** Dedicated disabled-policy suppression, risk-threshold equality, and event-append failure-containment coverage require further assessment. Best-effort workflow persistence does not establish universal outage resilience or durable replay.

### Events playback

- **Playback retrieval and response construction are different failure boundaries.** The [media route](../src/homesec/api/routes/media.py) retains Unicode alphanumeric identity characters in a manually constructed inline filename header. For identities such as `门口`, an encoder that cannot encode that header raises after successful storage retrieval; the generic pre-response response is 500, not storage-fetch 502. Minimal ASGI checks reproduced this with container-installed dependencies, not a freshly installed repository lockfile. The guard/filename cases remain pending at the mounted repository boundary.
- **Each media request stages locally before delivery, and cleanup has gaps.** The same media route creates a temporary directory and awaits `storage.get()` before constructing `FileResponse`; there is no route cache/reuse or direct storage streaming. File-response range handling follows that fetch. Normal retrieval exceptions request cleanup; completed responses run attached background cleanup. Cancellation during retrieval or response-construction failure before cleanup is attached can leave staging. These directories are not automatically registered with recording retention. Isolated checks do not claim that external OS cleanup never removes them.
- **Query tokens are not the only playback authorization.** With authentication enabled, a valid bearer API key is accepted before query-token validation; disabled authentication skips tokens. Scope/expiry rejection scenarios assume token authorization is actually used. Earlier mode/database gates still apply. See the [shared API admission contract](../openspec/specs/integration-contracts/spec.md#shared-api-preconditions) and [authorization helpers](../src/homesec/api/dependencies.py).

Event views expose the currently stored snapshot. Even successful queries and row hydration do not certify preservation of all earlier stage metadata or independent identity for separate ingestions; the [concurrent-write](#analysis-alerts) and [clip-ID collision](#capture-recording) limits also apply.

- **Deleted records remain addressable by identity.** Default lists exclude deleted clips, while an explicit deleted-status filter can include them. Detail and media-token lookups do not reject `DELETED` records, whose metadata and storage URI can remain. A token/media URL can therefore still be returned. Fetching a removed stored object returns HTTP 502 `CLIP_MEDIA_FETCH_FAILED` if retrieval raises; playback can still succeed if deletion failed, the object remains retrievable, and response construction/delivery also succeed. Status-aware lookup/playback and deletion retry semantics remain unresolved. See the [clip routes](../src/homesec/api/routes/clips.py), [media route](../src/homesec/api/routes/media.py), and [Postgres store](../src/homesec/state/postgres.py).
- **Lookup failures can look like missing clips.** The availability guard can pass before a query or hydration failure. The default store converts such failures to `None`, bypassing repository retries; exhausted repository lookup exceptions also become `None`. Detail, token, media, and delete can then return HTTP 404 `CLIP_NOT_FOUND`. Unknown-identity guarantees assume successful lookup; 404 alone is not proof of absence. See the [repository](../src/homesec/repository/clip_repository.py).
- **List failures can look like successful empty or incomplete searches.** After authentication and the database availability check succeed, a later list-query failure can still produce HTTP 200 with `clips=[]`, `next_cursor=null`, and `has_more=false`. The default Postgres store logs connection/query failures and returns that empty page, so repository retries are not triggered; exceptions that reach the repository produce the same empty page after retry exhaustion. Rows that fail hydration are logged and omitted, while pagination is calculated from the fetched rows before hydration. A short or empty page is therefore not proof that no other matching events exist, and HTTP 200 does not certify a complete result set. See the [Postgres store](../src/homesec/state/postgres.py), [repository](../src/homesec/repository/clip_repository.py), and [clip routes](../src/homesec/api/routes/clips.py). This is a source-supported limitation, not an intended failure policy; focused characterization coverage remains pending.
- **Playback timing coverage is incomplete.** Refresh calculations and retry helpers have tests, but a complete mounted-hook timer test was not identified. Event cards currently acquire media eagerly; activation-only loading remains pending work, and the baseline does not require a prefetch schedule.

### Preview talk

- **Preview and talk tokens are fallback authorization paths.** A valid bearer API key bypasses accompanying query-token validation, and disabled authentication skips it. Preview token lifetime bounds a negotiated lease only when the token is the authorization used. The talk socket is accepted before its authorizer runs; token rejection closes that accepted socket before runtime-stream opening. See [dependencies](../src/homesec/api/dependencies.py), [preview routes](../src/homesec/api/routes/preview.py), and [talk routes](../src/homesec/api/routes/talk.py).

- **Cancelling the authorized first-message wait can leave a talk reservation.** In the [WebSocket handler](../src/homesec/api/routes/talk.py), the first start-message wait occurs before the runtime-stream cleanup `try/finally`. A returned disconnect or start timeout requests best-effort stop, but task cancellation at that await propagates without a stop request. Streaming has not started; this is a reserved-slot cleanup gap, not evidence of continued microphone transmission. The reservation can remain until the [source manager](../src/homesec/sources/rtsp/talk/manager.py) releases it through its existing `max_session_s` timer or another successful cleanup action. An isolated source-excerpt harness reproduced zero stop requests on cancellation versus one for disconnect and timeout. Repository-level reservation-lifetime coverage remains pending; immediate cancellation cleanup needs a separately reviewed runtime fix.

- **Native viewer-cap coverage is bounded.** The native integration test `malformed_offers_and_negotiation_timeout_release_admission_capacity` in [media delivery tests](../native/webrtc/tests/media_delivery.rs) fills a one-session cap, asserts `session_limit`, and verifies admission capacity returns after negotiation timeout. That test was inspected during this correction, not executed locally. It provides focused admission/release coverage; broader camera, codec, browser, microphone, and physical-device QA remains a follow-up. Deployment guides are not a universal compatibility certification.
- **Talk duration limits apply to separate phases.** The reservation timer starts at preparation and is replaced by an active-session timer when activation succeeds. The WebSocket first-message deadline starts after connection/authentication, not at HTTP preparation. These origins are source-supported; a focused total-lifetime timer test was not identified. Timer expiry invokes stop, which clears the matching record before awaiting session I/O/closure; detecting expiry is not proof that backend cleanup has already completed. See the [talk manager](../src/homesec/sources/rtsp/talk/manager.py) and [talk routes](../src/homesec/api/routes/talk.py).

### Integration contracts

- **Generated error schemas can disagree with actual envelopes.** The [exporter](../src/homesec/api/openapi_export.py) reflects declared models, but [custom error handlers](../src/homesec/api/errors.py) do not automatically replace FastAPI's error schemas. For example, the declared setup connection-test 422 uses `HTTPValidationError` with array-valued `detail`, while a JSON-safe invalid request actually returns string-valued `detail`, `error_code`, and `validation_errors`. A fresh export and the actual mounted contract route reproduced that mismatch using a fake application, with no lifespan/runtime or database operations. Treat the maintained error contract as authoritative for these custom envelopes; the generated schema alone is not an exact description. Schema correction is separate work.

- **Validation-error serialization can replace 422 with 500.** The [error handler](../src/homesec/api/errors.py) inserts `exc.errors()` directly into `JSONResponse`; a model-validator exception in `ctx.error` is not JSON-safe. The integral PCM-frame validator can trigger this with `sample_rate: 11025` and `frame_ms: 20`, yielding generic pre-response 500 rather than 422. Isolated ASGI checks include a normal validation-error control; locked-environment mounted-route coverage remains pending. This is a serializer defect, not the intended validation policy.
- **Malformed non-ASCII credentials can produce 500 rather than 401.** [API-key comparison](../src/homesec/api/dependencies.py) uses `secrets.compare_digest` on strings. A parsed non-ASCII bearer value can raise `TypeError` and become a generic pre-response HTTP 500 instead of ordinary mismatch rejection. No protected route is admitted. WebSocket close/error handling is separate; it is not this HTTP envelope. Isolated ASGI checks are not a locked full-application test.

- **Production notifier fan-out needs focused mixed-success coverage.** The pipeline dispatches per enabled entry and records individual outcomes. `MultiplexNotifier` helper tests exercise a different path, so they do not establish that one production-entry failure leaves other delivery intact. See the [pipeline](../src/homesec/pipeline/core.py).
- **Plugin examples can lag the current registry.** Current extension contracts use the unified class-based registry and external `homesec.plugins` entry points. Older AGENTS examples use per-type factory/context patterns, and some plugin-guide examples use `type` where the decorator accepts `plugin_type`. Use the [registry source](../src/homesec/plugins/registry.py), [discovery source](../src/homesec/plugins/__init__.py), and [interfaces](../src/homesec/interfaces.py) when reconciling those examples. The baseline does not promise automatic interface verification.
- **Installed plugin discovery and construction boundaries have limited tests.** External entry-point discovery, validate-before-factory behavior, and configuration-only paths that do not construct components are source-supported; dedicated end-to-end/boundary coverage was not identified for all those paths.

### Operations maintenance

- **Housekeeping can reclassify a completed dump as failed.** In the [backup manager](../src/homesec/maintenance/postgres_backup.py), a broad run-level error handler covers finalization, upload, retry work, and retention. A new finalized dump whose upload failed can be marked `failed` when deleting an older pending artifact raises. Its file can remain while subsequent pending-upload retries skip it because they require status `success`. A temporary-file/fake-dump harness reproduced this and a successful-housekeeping control; full manager lifecycle coverage remains pending. This is distinct from the unsaved cancellation marker and from dump-integrity verification.

- **Health summaries and diagnostics answer different questions.** Their degradation criteria differ. A successful summary is not proof that every camera and storage dependency is healthy; inspect component diagnostics and camera counts. Some architecture-document wording conflates the surfaces. See the [health routes](../src/homesec/api/routes/health.py).
- **Zero statistics can hide a count-query failure.** Individual repository counts can fall back to zero after an earlier availability check passed. Counts are UTC-day clip-level observations; a zero is not proof of no activity. See the [repository](../src/homesec/repository/clip_repository.py).
- **Exit code 42 is not a reachable public setup contract.** `request_restart()` has no production callers, setup activates in-process, and the CLI test forces the restart flag with a mock. The baseline excludes that branch; dead-code cleanup remains separate.
- **Backup recovery does not prove dump integrity or successful restore.** Recovery recognizes artifact names/metadata, and unit tests fake dump output. Missing-executable startup degradation and private artifact permissions are source-supported with limited focused coverage. No real dump/restore round trip was verified for this baseline. Persisting the local backup directory/manifest and performing restore procedures remain operator responsibilities. Retention is not a universal backup disk bound. Unknown-outcome markers protect retained local artifacts from pending-upload pruning, but that protection across restart depends on the saved manifest, as described below. Follow the [backup guide](postgres-backups.md).

- **Cancelling a startup upload retry can lose its unknown-outcome marker.** The [backup manager](../src/homesec/maintenance/postgres_backup.py) sets `pending_upload_unknown` in memory when an upload is cancelled. The new-backup path has a manifest-saving `finally`, but the startup storage-retry task re-raises cancellation without saving the changed record; its upload-retry loop also saves only after normal loop completion. After restart, an older ordinary `pending_upload` record can therefore be recovered. Later failed retries and `keep_count` pruning can remove that local retry handle despite an uncertain earlier remote outcome. A subsequent successful save of the unknown-outcome marker preserves the pruning exemption. An isolated source-excerpt harness with temporary manifests and fake storage reproduced the loss and the saved-marker control; full manager startup/shutdown/restart coverage remains pending. This limitation is distinct from dump-integrity verification and is not a policy to preserve.

## API schemas and commands

The [OpenAPI exporter](../src/homesec/api/openapi_export.py) builds the schema from registered API routes and models. The [UI generation script](../ui/scripts/api_codegen.mjs) uses that exporter to produce the committed [OpenAPI JSON](../ui/src/api/generated/openapi.json), [TypeScript schema](../ui/src/api/generated/schema.ts), [types](../ui/src/api/generated/types.ts), and [client](../ui/src/api/generated/client.ts). Those generated files describe declared request/response models. Custom error handlers can disagree with generated error schemas, as described in [integration limitations](#integration-contracts); use the maintained error-envelope contract for those responses. Capability specs also provide behavior that schemas cannot express.

From the repository root, export a standalone schema:

```bash
uv run --locked python -m homesec.api.openapi_export --output /tmp/homesec-openapi.json
```

Use the existing UI commands to regenerate or check committed contracts:

```bash
pnpm --dir ui api:generate
pnpm --dir ui api:check
```

Configuration fields and validation come from the [core configuration models](../src/homesec/models/config.py), [loader](../src/homesec/config/loader.py), and each plugin's configuration model. There is no complete exported plugin-configuration reference today. Validate an operator's configuration and inspect current CLI options using the existing commands:

```bash
uv run --locked homesec validate --config config.yaml
uv run --locked homesec --help
uv run --locked homesec cleanup --help
```

Internal refactors that preserve public behavior need no invented behavior delta. Review documentation corrections separately from intentional behavior changes.
